## Objetivo

Construir únicamente el marco visual reutilizable de la experiencia Hospital para que el Product Owner pueda reconocer en localhost la interfaz aprobada en Claude Design.

El resultado debe incluir exclusivamente:

1. estructura general persistente;
2. sidebar azul;
3. identidad institucional;
4. menú completo;
5. topbar;
6. buscador visible;
7. campana de notificaciones; y
8. perfil visible.

No se autoriza implementar el contenido de ninguna sección, lógica de negocio, backend, integración, autenticación ni permisos.

## Contexto y valor para el producto

Esta microtarea establece la envolvente visual común de la experiencia Hospital antes de construir sus pantallas internas. Debe permitir validar tempranamente la fidelidad del lenguaje visual y crear componentes de presentación reutilizables para los siguientes microbloques, sin anticipar arquitectura de dominio ni comportamiento funcional.

La experiencia Hospital es una experiencia institucional diferenciada construida sobre capacidades compartidas de MERDN. Este shell no debe crear una aplicación aislada ni asumir que existe una sola institución.

## Requisitos funcionales y visuales

### FR-01 — Estructura del shell

1. Crear una superficie de revisión Hospital accesible mediante una URL localhost estable, preferiblemente `/hospital`, sin reemplazar ni degradar experiencias existentes.
2. El shell debe ocupar como mínimo toda la altura visible y mantener sidebar, topbar y área de contenido como regiones diferenciadas.
3. Sidebar y topbar deben estar implementados como componentes reutilizables, no como un único archivo monolítico.
4. La implementación debe ser React/TypeScript mantenible y usar estilos compatibles con la arquitectura existente de `apps/web`.

### FR-02 — Identidad multi-institución

1. Centralizar en una única configuración tipada los datos demostrativos siguientes:
   - nombre de institución: `Hospital San Rafael`;
   - tipo de institución: `ESE`;
   - municipio: `Soacha`;
   - logo: ausencia de logo específico en el prototipo, con estructura preparada para recibirlo posteriormente;
   - nombre de usuario: `Claudia Vargas`;
   - rol: `Coordinación domiciliaria`;
   - iniciales: `CV`; y
   - conteo demostrativo de novedades: `7`.
2. Los componentes visuales deben recibir esa información mediante propiedades o un objeto de configuración; no deben repetirla ni fijarla internamente en múltiples componentes.
3. No crear proveedor remoto, API, contexto global definitivo, persistencia ni mecanismo de tenant en esta tarea.
4. No presentar los datos demostrativos como identidad global de MERDN.

### FR-03 — Navegación exclusivamente visual

1. Renderizar todos los elementos del menú en el orden y con los iconos del prototipo.
2. `Inicio` debe aparecer visualmente activo para la revisión inicial.
3. Los demás elementos deben conservar su estado inactivo.
4. No implementar rutas internas, cambio de sección, contenido condicional ni navegación funcional.
5. Los elementos no deben usar enlaces falsos, `href="#"` ni acciones que recarguen o desplacen la página.
6. Si se representan con botones, deben ser semánticamente válidos, tener `type="button"` y no ejecutar acciones.
7. No comunicar mediante atributos ARIA que una sección está operativa cuando aún no lo está. El estado activo visual de `Inicio` puede exponerse como estado actual solo si no induce una navegación inexistente.

### FR-04 — Buscador, campana y perfil

1. Reproducir fielmente el buscador del prototipo.
2. En esta tarea el buscador es solo visual: no consulta, filtra ni almacena información.
3. Si se usa un campo real, debe tener nombre accesible y permanecer sin integración; si se usa una representación no editable, su semántica no debe sugerir funcionalidad disponible.
4. Reproducir la campana y su badge demostrativo sin abrir paneles ni modificar conteos.
5. Reproducir el perfil sin menú, autenticación, cierre de sesión ni administración de cuenta.

### FR-05 — Iconografía y fidelidad

1. Reproducir los SVG inline observados en la referencia o encapsularlos en componentes locales reutilizables sin alterar su geometría visual.
2. No introducir una librería de iconos.
3. No sustituir los iconos por emojis, caracteres Unicode o variantes visuales aproximadas.
4. Conservar `fill="none"`, trazo mediante `currentColor`, grosor y terminaciones visibles de la referencia.
5. Conservar la familia Nunito con pesos equivalentes a `400`, `600`, `700`, `800` y `900`, usando el mecanismo ya permitido por Next.js si resulta apropiado y sin añadir paquetes.

### FR-06 — Responsive

1. En el viewport de referencia de Claude Design (`1320 × 900`), la composición debe coincidir visualmente con el prototipo.
2. El layout no debe producir solapamientos, contenido cortado horizontalmente ni pérdida de acceso visual a topbar o menú en anchos menores.
3. La adaptación responsive debe preservar identidad, navegación, buscador, campana y perfil; no debe eliminar silenciosamente elementos requeridos.
4. Puede emplearse una adaptación estructural mínima —por ejemplo, navegación apilada o sidebar desplazable— únicamente cuando el ancho disponible no permita conservar la composición de escritorio.
5. No diseñar una navegación móvil nueva, drawer, menú hamburguesa ni interacción no presente en el prototipo sin una aprobación posterior.
