## Objetivo

Completar únicamente la parte superior del área blanca ya existente en `/hospital` con el encabezado de Inicio y las siete tarjetas KPI operativas aprobadas en Claude Design.

El resultado visible debe contener exclusivamente:

1. la etiqueta `CENTRO DE CONTROL OPERATIVO`;
2. el título `Atención domiciliaria de hoy`;
3. la fecha y hora demostrativas de la referencia; y
4. las tarjetas KPI de citas, visitas domiciliarias, consultas virtuales, alarmas, pacientes, profesionales y asignaciones, incluidos sus desgloses.

La zona situada debajo de la cuadrícula debe permanecer vacía. Esta tarea no autoriza ningún otro bloque del Dashboard ni funcionalidad de aplicación.

## Contexto y valor

TASK-003H-01 estableció la envolvente persistente del Hospital. Esta microtarea añade el primer bloque de contenido reconocible sin alterar esa envolvente y deja una interfaz de componentes y datos apta para reemplazar posteriormente los valores demostrativos por datos reales.

Los KPIs son una representación visual demostrativa, no indicadores oficiales ni métricas productivas. La tarea no define fuente, fórmula, periodo operativo, actualización, autorización o linaje definitivo.

## Usuarios, institución e impacto

- **Experiencia:** Hospital, pantalla Inicio/Dashboard.

## Requisitos funcionales y técnicos

### FR-01 — Integración mínima con el shell

1. Conservar exactamente `HospitalSidebar`, `HospitalTopbar`, buscador, perfil, navegación global, identidad, badges y comportamiento responsive ya implementados.
2. Sustituir únicamente el contenido vacío de `HospitalShell` por el bloque superior del Dashboard.
3. Mantener `/hospital` como superficie de revisión; no crear rutas nuevas ni modificar otras experiencias.
4. No convertir el shell en un componente cliente si no existe una necesidad autorizada.
5. La zona posterior a la cuadrícula no debe renderizar placeholders, mensajes, skeletons ni anticipos de bloques futuros.

### FR-02 — Componentes reutilizables y contrato de datos

1. Crear o reutilizar un componente de composición equivalente a `HospitalDashboardHeader` para etiqueta, título y fecha.
2. Crear o reutilizar un componente genérico equivalente a `HospitalKpiCard`; una sola implementación debe representar las siete tarjetas mediante propiedades tipadas.
3. Crear o reutilizar un contenedor equivalente a `HospitalKpiGrid` o una composición igualmente clara que itere sobre la configuración.
4. Definir un contrato tipado de presentación que, como mínimo, reciba `label`, `value`, `accentColor`, `iconBackground`, `icon` y una lista ordenada de pares de desglose.
5. Centralizar los siete fixtures demostrativos fuera del JSX de la tarjeta. El componente visual no debe conocer categorías concretas, sumar valores, derivar estados ni contener condicionales de negocio por tipo de KPI.
6. Conservar el orden de entrada y admitir una cantidad variable de filas de desglose sin variantes copiadas de la tarjeta.
7. Los valores pueden tiparse como texto de presentación para no imponer hoy formato, unidad o precisión productiva.
8. No crear un modelo de dominio definitivo, store, contexto global, hook de fetching, endpoint ni capa de servicios.

### FR-03 — Iconografía

1. Reutilizar `HospitalIcon` cuando ya contenga exactamente la geometría requerida para calendario, casa, video, alerta, usuarios y estetoscopio.
2. Extender de forma mínima el catálogo local para el icono de reloj si no existe; no alterar la geometría ni el render de los iconos actuales.
3. No introducir una librería de iconos, emojis, Unicode, imágenes raster ni Canvas.
4. Los iconos son decorativos porque la etiqueta textual comunica el KPI; deben ocultarse de tecnologías de asistencia y no recibir foco.

### FR-04 — Responsive y fidelidad

1. En `1320 × 900`, reproducir la parte superior de `vInicio` sin rediseño, simplificación ni omisiones.
2. Preservar el grid `auto-fit/minmax` de referencia siempre que resulte compatible con la estructura existente.
3. En viewports menores, encabezado y tarjetas pueden hacer wrap según las reglas ya presentes; no deben solaparse, cortarse, provocar overflow horizontal ni reducir el contenido del KPI hasta hacerlo ilegible.
4. No ocultar tarjetas, desgloses, título ni fecha en responsive.
5. No cambiar sidebar/topbar para resolver el responsive de este bloque.

### FR-05 — Accesibilidad

1. Mantener un único contenido principal semántico y una jerarquía de encabezados coherente.
2. La etiqueta superior no debe sustituir al encabezado visible `Atención domiciliaria de hoy`.
3. Cada tarjeta debe constituir un grupo comprensible; lector de pantalla debe poder asociar etiqueta, total y desgloses sin depender del color o el icono.
4. Los pares de desglose deben conservar relación semántica clara; puede usarse una lista o descripción estructurada equivalente sin alterar la apariencia.
5. No añadir controles interactivos, tab stops ni estados ARIA de widgets a contenido meramente informativo.
6. El color no debe ser el único medio para identificar cada métrica: las etiquetas y textos visibles son obligatorios.
